# M7.76: Ascension guest VM boot audit

This change addresses the first measured guest-side stall in the supplied
M7.75 session video. It does not claim that a menu or gameplay frame has been
produced.

## What the session proves

- The pinned PS3Recomp lift registers 29,849 PPU entries and four SPU images.
- The actual guest AOT entry starts and executes. The HLE dispatcher reports
  calls, with no unresolved HLE at the captured stop. The most recent LV2 call
  is syscall 330 (`sys_mmapper_allocate_address`).
- The guest never calls `cellFsOpen` or `cellFsRead`, and produces no guest RSX
  draws or flip. Metal vblank and FIFO-drain counters are host-worker activity,
  not evidence of a game frame.
- The AOT report captures `func_003C4F98` looping at `0x003C4FA4` with
  `r3=0x11019000`, `r9=0`, and the key in `r4=0x1C5C`.

## Root cause

The production adapter used `calloc(256 MiB)` and passed that same size to
PS3Recomp as `ppu_vm_size`. The guest's `0x11019000` address is outside that
window. PS3Recomp's bounded `vm_read32` therefore returned zero, and bounded
stores to the same address were dropped. The game could not initialize the
tree/sentinel state that the captured AOT function searches; it repeatedly
followed the zero link. This explains the changing loop counter without guest
filesystem or renderer progress.

## Correction

M7.76 reserves a 4-GiB-aligned 4-GiB virtual range, exposes a 3.5-GiB guest
window, and commits pages lazily for the low guest range (`0x00000000` through
`0x50FFFFFF`), RSX local memory (`0xC0000000` through `0xCFFFFFFF`), and the PPU
thread-stack band (`0xD0000000` through `0xDFFFFFFF`). It does not zero or
physically allocate the whole range up front. The `0x11019000` game state is
now readable and writable by both the boot loader and PS3Recomp; the same
window is supplied to `ppu_vm_size`.

This follows the virtual-address and guest-region approach in the GoW2
reference host. The Ascension PC launcher informed the launcher sections for
the game, files, and execution status, but a PC status display is not used as
evidence of iPhone boot.

## Validation and the next gate

The host regression test checks 4-GiB alignment, guest reads/writes at the
observed mmapper address, RSX-local memory and the thread-stack band, plus
rejection at the 3.5-GiB bound. Actions runs this test before building the iOS
IPA.

The first on-device gate after this fix is non-zero guest `cellFsOpen`/`Read`
activity. The next is guest RSX draws and a guest flip presented by Metal. Until
those counters advance, the launcher explicitly reports that boot is not
proven. If a later guest stop appears, its new PC/register report identifies
the next specific missing service or state; the old `0x003C4FA4` loop must no
longer be used as a generic progress counter.
