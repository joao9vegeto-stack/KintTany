# M7.77: LiveContainer VM reservation and launcher audit

## What the M7.76 video proves

The supplied `IMG_5042.mov` ends before the PS3 guest is loaded:

- The host reports `host rc=-7`, `entry=0`, zero `PT_LOAD` bytes, zero guest
  VM capacity, zero AOT entry starts, and no configured guest VFS.
- In `ppu_bridge.h`, `-7` is `AR_NO_MEMORY`. `ar_m70_native_runtime_probe`
  returns it directly when `ar_bridge_init` cannot reserve guest memory.
- Therefore this run did not test the M7.76 correction for the former guest
  loop at `0x003C4FA4`. It stopped before ELF parsing and before any guest AOT,
  HLE, `cellFs`, or RSX command could run.

## Why the reservation failed

The pinned PS3Recomp VM converts host pointers back to PS3 effective addresses
using the low 32 bits. Its `runtime/memory/vm.h` requires a `vm_base` aligned
to 4 GiB. GoW2's host uses the same PS3 guest address window and sparse VM
region model. Removing that alignment would make guest pointers incorrect.

Before M7.77, Ascension requested one contiguous 8-GiB `PROT_NONE` mapping,
then unmapped half to find a 4-GiB-aligned 4-GiB window. That wastes address
space in LiveContainer and failed before the loader could expose an `errno`.

## M7.77 changes

- Try a set of ordinary 4-GiB-aligned address hints, reserving only the exact
  4-GiB guest window. The code never uses `MAP_FIXED`; a relocated hint is
  released and the next candidate is tried.
- Keep the existing 8-GiB over-reserve-and-trim path as a fallback.
- Preserve the 3.5-GiB visible guest capacity and lazy low-memory, RSX, and
  stack permissions required by the PS3Recomp address model.
- Capture reservation strategy, hint attempts, failure stage, and `errno`;
  include those values in the iPhone run report when the loader returns
  `AR_NO_MEMORY`.
- Split the launcher into **Jogar**, **Arquivos**, and **Relatório**. The
  report is directly accessible and refreshes during a guest run. The home
  screen now shows guest AOT calls, guest filesystem bytes, and guest RSX
  draws/flips; host FIFO/vblank worker activity is kept out of the progress
  card.
- Keep the synthetic RSX bench out of the game setup flow. It does not
  initialize Ascension and is not a boot milestone.

## Validation and next device gate

`tests/host_m772_sparse_vm.c` verifies the aligned-hint route on the build
host, the 4-GiB base alignment, writes to the observed mmapper address,
RSX-local memory and the stack band, and rejection beyond the 3.5-GiB guest
window. The iOS Actions build reuses the M7.76 PS3Recomp archive only after
its pinned commit, ABI, symbol list, and SHA-256 attestation match; the
launcher and VM bridge are rebuilt from M7.77 source.

The next device report must show non-zero guest entry starts. After that,
guest `cellFsRead` bytes establish game-data access, guest RSX draws establish
commands, and a presented guest flip establishes the first game frame. A
successful IPA build or host VM regression does not establish those iPhone
milestones.
