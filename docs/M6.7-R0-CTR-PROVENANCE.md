# AscensionRecomp M6.7 — provenance of a non-executable bctrl target

Physical screenshot M6.6.3 on iPhone, NPUA80918 GOWA.ELF imported locally:
- Previous M6.4 28/32 -995 stack-only stw; M6.5 38/40 -990 mtctr,
  both correctly transferred to newer checked stages.
- M6.6 PPU48 stops safely after 39 instructions, PC=0x669C30,
  opcode=0x4E800421 (bctrl), CTR=0x39800000, error -1007.
- Target is NOT a recognized executable guest PT_LOAD. It must not
  be treated as a host pointer or an automatically mapped PS3 address.

M6.7 does NOT relax destination validation or invent a jump. It is
a diagnostic iteration using exactly the same bounded PPU48 core.
The existing ar_ppu_bootstrap_fortyeight API remains unchanged and
is a wrapper around an optional 24-word trace function:
- last actual r0 modification: PC, opcode, prior value, resulting
  64-bit value, count of value changes, opcode class, effective
  address if the writer was lwz/ld;
- mtctr PC, source register and captured CTR value;
- last four executed PC/instruction words in a circular buffer;
- current opcode memory EA cleared every iteration and only
  displayed if the error is a memory error.
No file bytes, audio/gameplay, game code or RAP are embedded in CI
or IPA. No guest native pointer dereferencing.

The Game/PPU tab retains import and has a new "Copiar diagnóstico PPU"
button, disabled until a trace report exists. After importing,
the user can copy one text report and paste it to ChatGPT instead
of sending multiple screenshots. The UI still displays a concise
safe-stop result. Version 0.6.13 build 65.

Host tests use synthetic ELF and confirm tracing does not change
the correct bctr/bctrl behavior, and an invalid CTR still returns
-1007, with the original r0 writer PC/opcode and four-step history.
The next action is to inspect the on-device diagnostic and identify
why r0 contains 0x39800000. Do not bypass the bctrl guard before
resolving the source of the register value and legitimate code map.
