# M7.83: SPURS2 workloads 16–31 and dispatch evidence

## Finding from the M7.82 device capture

The displayed `0x003C4FA4` was the last observed backedge marker from `func_003C4F98`; it was never a continuously sampled instruction PC. The capture's actual AOT entry was `0x0066640C`, with guest filesystem reads and SPURS HLE activity, but the RSX path still had zero guest draws and zero presented flips.

Comparison against the Ascension PC port identified a runtime gap: its SPURS2 path supports 32 workloads. The second set stores ready counts at instance `+0x10`, signals at `+0x78`, state at `+0xD0`, policy descriptors at `+0x1000`, and is selected by the `0x40` flag at `+0x74`. The pinned iOS runtime supported only the first 16. In the PC port, the omitted `EDGE1`, `EDGE2`, and `RsxSync` jobs blocked the frame-end path.

## M7.83 change

The pinned PS3Recomp runtime now expands workload and policy-module slots to 32, initializes and bounds-checks the 8 KiB SPURS2 object, routes ready/state/signal/descriptor accesses through the correct set, and lets the per-SPU scheduler scan IDs 0–31. First-generation SPURS instances stay limited to 16. The RSX mapper's strict-ordering validation remains intact.

The live report now exposes SPURS2 initializations, workload registrations (including IDs 16–31), resolved and missing policy modules, scheduler dispatches, and the last dispatched workload ID. It labels `0x003C4FA4` as an old loop marker and explicitly says instruction-level PC is not measured.

## Audit of `IMG_5053_compressed.MOV`

The screen capture's report shows `last AOT entry=0x0066640C`, caller LR `0x0049CD88`, `unresolved HLE=0`, and the historical loop marker `0x003C4FA4`. In the lifted source, `func_0066640C` is an import stub that dispatches NID `0x80A29E27`; `func_0049CD6C` is the caller. This is a serviced HLE call, not evidence that the guest instruction PC is stuck at the import address.

The original ELF and its whole-title AOT lift identify `func_003C4F98` as a tree search. At label `0x003C4FA4` it reads the current node, compares the key, follows a child through `0x003C4FF8`, and either returns at `0x003C5004`/`0x003C5008` or branches back to search the next node. The video counter changes from 57,613 to 57,813 during the capture, so this marker is being revisited; it does not identify a frozen current PC.

The same report records 47 guest opens (37 successful), 240 guest reads, and 11,527,017 bytes read, while the summary line still says that the configured VFS has not been proven. That wording was stale because it depended only on the root-configured flag. M7.83 now derives the summary from live guest read calls and bytes, while leaving the exact file path and PSARC identity unclaimed. The graphics counters remain the actual blocker in this capture: Metal initialized and the FIFO worker ran, but guest draws and presented flips were both zero.

## What this establishes

The source path and build attestation establish that the 32-workload implementation is present in the ARM64 runtime. They do not establish that a device run registers an `EDGE1`/`EDGE2`/`RsxSync` workload, resolves its policy module, dispatches it, or presents a game frame. The next device report distinguishes those stages; menu/gameplay are only confirmed by guest RSX draws and a guest flip.

## CI link-gate correction

The first M7.83 Actions run compiled all 29,849 AOT functions into the ARM64 archive, then stopped because the AOT-only symbol gate incorrectly required `_cellSpursResetAscensionMetrics` and `_cellSpursCopyAscensionMetrics`. Those functions are provided by the separately compiled PS3Recomp runtime. The gate now checks them in the iOS runtime symbol list, while the AOT archive and reusable AOT cache attest only symbols they own. This avoids rejecting a completed native lift for symbols that correctly live in its runtime dependency.
