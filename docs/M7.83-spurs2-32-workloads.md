# M7.83: SPURS2 workloads 16–31 and dispatch evidence

## Finding from the M7.82 device capture

The displayed `0x003C4FA4` was the last observed backedge marker from `func_003C4F98`; it was never a continuously sampled instruction PC. The capture's actual AOT entry was `0x0066640C`, with guest filesystem reads and SPURS HLE activity, but the RSX path still had zero guest draws and zero presented flips.

Comparison against the Ascension PC port identified a runtime gap: its SPURS2 path supports 32 workloads. The second set stores ready counts at instance `+0x10`, signals at `+0x78`, state at `+0xD0`, policy descriptors at `+0x1000`, and is selected by the `0x40` flag at `+0x74`. The pinned iOS runtime supported only the first 16. In the PC port, the omitted `EDGE1`, `EDGE2`, and `RsxSync` jobs blocked the frame-end path.

## M7.83 change

The pinned PS3Recomp runtime now expands workload and policy-module slots to 32, initializes and bounds-checks the 8 KiB SPURS2 object, routes ready/state/signal/descriptor accesses through the correct set, and lets the per-SPU scheduler scan IDs 0–31. First-generation SPURS instances stay limited to 16. The RSX mapper's strict-ordering validation remains intact.

The live report now exposes SPURS2 initializations, workload registrations (including IDs 16–31), resolved and missing policy modules, scheduler dispatches, and the last dispatched workload ID. It labels `0x003C4FA4` as an old loop marker and explicitly says instruction-level PC is not measured.

## What this establishes

The source path and build attestation establish that the 32-workload implementation is present in the ARM64 runtime. They do not establish that a device run registers an `EDGE1`/`EDGE2`/`RsxSync` workload, resolves its policy module, dispatches it, or presents a game frame. The next device report distinguishes those stages; menu/gameplay are only confirmed by guest RSX draws and a guest flip.
