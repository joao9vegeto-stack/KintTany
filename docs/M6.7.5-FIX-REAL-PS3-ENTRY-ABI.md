# AscensionRecomp M6.7.5 — fix missing LV2 process-entry registers, not HLE args

## Proof from private physical NPUA80918
M6.7.3: 39 PPC steps to import sysPrxForUser NID 0x744680A2
at stub 0x00669C0C. The old code treated two PPC instructions
as a function descriptor, giving CTR 0x39800000.
M6.7.4: same stop after 39 steps, but return code -1011.
Recognized HLE got r3..r6 ALL ZERO and declined initialization.
That is NOT evidence the TLS function should take no args.
It proves the sample interpreter failed to supply a real process
entry context. Previous host test had hard-coded gpr3..6, hiding it.

## Root mechanism
PS3Recomp process-entry ABI, in its runtime/ppu/ppu_loader.cpp:
r7=nonzero main-thread ID,
r8=ELF PT_TLS template VA,
r9=PT_TLS filesz,
r10=PT_TLS memsz,
r12=0x00100000 (LV2 page size).
The real guest CRT forwards these into r3..r6 before invoking
sys_initialize_tls. The prior sandbox set only r1/r2, leaving
r7-r10/r12 zero and causing failure even with a correct HLE.

M6.7.5 changes ONLY the opt-in TLS-aware PPU48 entry path:
- Read genuine PT_TLS (p_type=7) from the chosen private ELF,
  validate duplicate headers, 32-bit VA, 0<=file<=mem<=16KiB,
  and check file-backed bytes live inside a loaded PT_LOAD.
- Seed process entry registers r7..r10 from ELF, r12=1 MiB.
- Never directly overwrite HLE arguments r3..r6. The PPC
  instructions have to forward them as authored.
- Keep exact NID/library/stub matching, bounded TLS copy/BSS
  zeroing, r13 thread pointer, caller return, and -1007 guard.
- -1021 means unsafe or malformed PT_TLS descriptor.
- Diagnostic now exposes PT_TLS presence and original LV2 page size.
- Original untraced/traced M6.6 and M6.7 APIs remain unchanged.

Host synthetic test mirrors actual guest CRT forwarding with PPC
ORI instructions r7->r3, r8->r4, r9->r5, r10->r6. It proves the
verified TLS initialization and caller return, unknown NID remains
rejected, malformed/unmapped PT_TLS is rejected early, and an
ELF with no PT_TLS is handled safely without assuming game data.
