# XOWUE Build 131.5 — dispatcher atomicity and movie-transition diagnostics

Base commit: `79ed5153a7ae4e5581dbe70c24bcb744e40b339b` (Build 131.4).

## Evidence from the iPhone diagnostic

The uploaded Build 131.4 runtime trace shows that the XEX loads, the Xenos/KosmicKrisp Vulkan-to-Metal backend and swapchain initialize, and the title produces some early guest submissions. It does **not** establish that the menu was reached.

At the end of the capture:

- The main guest thread is still executing at PPC PC `0x824ACC1C`, inside the routine beginning at `0x824ACBF8`.
- The video workers are not all complete; thread 12 is still associated with timer handle `0x116`.
- `XOWUE_GAME_FPS` and `XOWUE_FRAME_TELEMETRY` settle at zero guest VdSwap calls and zero guest content updates.
- The `UE3_logo.bik` file is read successfully through its final partial read. File EOF is not proof that Bink playback completed, that its guest completion object was signalled, or that the title advanced.
- Reads of other BIK files by asynchronous workers do not prove their playback order.
- The missing `blank.bik` lookup is recorded as a failed file lookup, but this trace alone does not prove that it is the cause of the menu stall.

The PPC state/list, Bink frame-state, and timer-wait correlation messages were generated by the runtime but were not all admitted by the bounded trace filter. The recurring media PPC emitter kept its established public prefix, but the bounded trace filter expected a different Build 105 label. Build 131.5 preserves the public prefix and adds it to the persistence allowlist.

## Runtime correctness correction

The previous `waitGuestObjects` implementation evaluated WaitAny/WaitAll by locking one dispatcher object at a time, released that lock, then reacquired the selected object(s) to consume the signal. A competing waiter could consume an auto-reset event or semaphore between those phases. That allowed an inconsistent multi-object decision and violated the NT dispatcher contract.

The corrected path:

1. Validates every referenced dispatcher object before beginning the wait.
2. Acquires all unique object mutexes together in a stable pointer order.
3. Evaluates readiness while the complete set remains locked.
4. Consumes the WaitAny-selected object or the complete WaitAll set without dropping any object lock.
5. Uses the same complete lock set in the condition-variable readiness predicate.
6. Registers the multi-object wait in `GuestWaitStateScope`, so a thread blocked in this path is visible to the existing stall snapshot.
7. Retains bounded 16 ms wait slices, scheduler cancellation, timeout semantics, alertable APC delivery, and the graphics watchdog.

This is a verified kernel-contract correction against the MW2 dispatcher semantics. It is **not yet proven to be the sole cause** of the specific main-thread PPC loop at `0x824ACC1C`, and it does not manufacture Bink completion or skip the movie.

## Cross-project comparison

- MW2 Recompiled documents one dispatcher lock over all object state and atomic WaitAny/WaitAll satisfaction. Its Xbox kernel object, timer, APC, and file semantics remain the primary reference for this part of the XOWUE runtime.
- MW2's iOS port also validates the need for larger host stacks for recompiled guest workers. XOWUE already has its own 16 MiB Apple guest-host stack path; this build does not change that path.
- Theft4's iOS startup notes provide a useful real-device AOT/runtime/presenter comparison: entry-point observation is explicitly distinguished from actual game execution, and its current release evidence uses repeated guest PM4 submits/presents and visible frames. It is not a Bink implementation to transplant into XOWUE.

## Regression coverage

- The existing Build 97 video diagnostic test now requires the recurring movie PPC flow, Bink state, SetState-list, circular-list, and timer-wait records to be both emitted and retained by the bounded trace filter.
- New `tools/test_xowue_wait_dispatch_semantics.py` enforces stable ordered locking, unique-lock acquisition, the same lock scope across readiness and consumption, and continued bounded waits.
- The XOWUE iOS workflow compiles and runs the new test before producing the IPA.

## Acceptance gates still required on the iPhone

A successful source test, compile, link, IPA, or Metal present is not a menu pass. The next device capture must show:

- recurring `XOWUE_MEDIA_PPC_FLOW` samples and `XOWUE_B90_BINK_STATE` progress across the visible `UE3_LOGO` ending;
- the `0x824ACBF8` state/list report (including cycle/truncation/invalid-next fields);
- the timer wait begin/result pair for thread 12 and handle `0x116`;
- a genuine PPC transition out of the observed SetState loop;
- continued guest VdSwap/frame serial progress after the logo, with changing guest pixels and no fabricated frames;
- the actual Wolverine menu rendered and responsive to the expected controller input.

Until those device-side gates pass, Build 131.5 is a correctness/diagnostic improvement, not a claim that the game has reached the menu.
