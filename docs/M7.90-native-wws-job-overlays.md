# M7.90: NPUA WWS jobs lifted to native ARM64

## What changed

The M7.87 report showed repeated SPURS policy admissions while the title's
job-chain counters stayed at zero. The runtime had a title-specific path for
WWS job overlays, but the pinned PS3Recomp code only enabled that path for
SPU image 2. The observed Ascension policy image is image 5 for the NPUA
module; the separately lifted C8 policy is image 6. M7.90 routes policy
handling by the registered PM name while preserving image 2 for existing
titles.

The workflow extracts the 31 `jobmod` overlays from the supplied digital NPUA
`GOWA.ELF` with the extractor used by the Ascension PC port, then lifts each
overlay through the `gowa-fixes` branch of PS3Recomp. This input yields 20,418
native functions across 31 job modules, with zero unclassified SPU words. The
resulting C translation units and one explicit registration function are compiled into
the iOS runtime archive. The app registers them during runtime initialization
with overlay identities 200 through 230. They are generated in the runner's
temporary directory; the raw input ELF, SELF, RAP, and `.bin` overlays are not
copied into the IPA or repository.

## ELF and SELF check

The input archive contains a big-endian PPC64 ELF for title `NPUA80918` and a
retail SELF with digital-license metadata. The ELF header, program-header
table, and section-header table match the corresponding metadata stored in
the SELF. This is a structural pairing check; the workflow does not decrypt
the SELF or compare every decrypted code segment. The supplied RAP is left
unread because the ELF already suffices for extraction and lifting, and the
platform SELF decryption keys are not part of this build environment.

The source is tied to the public revisions
[`gowa-pc` `45840d7`](https://github.com/RichardFontoura/gowa-pc/commit/45840d709a4e48a1d12d0803e323ba5c8568ab2a)
and [`ps3recomp` `f6ab60b`](https://github.com/RichardFontoura/ps3recomp/commit/f6ab60baf37662bd712592b7ef9f66891972a5fc).
The iOS link also patches the pinned upstream runtime
[`ps3recomp` `39a3629`](https://github.com/sp00nznet/ps3recomp/commit/39a36296511c445707adabcd312f0b740cfbd694).

## Data boundaries and translation gate

The stock job lifter treated all bytes in each module's executable section as
instructions. The US ELF has embedded string and constant data at the ends of
seven modules and a string island inside the `0xA00` policy module. Those bytes
were being emitted as `spu_unsupported()` sites, a logging/no-op path that
cannot run the guest instruction. M7.90 checks the return instruction or
constant signature at each boundary and checks that no direct branch targets
the excluded data. It excludes the internal string island only after checking
that it follows `bi $r0`, contains printable bytes, has no branch target, and
does not overlap a detected function.

The build rejects a lift if any unsupported SPU word remains. This matters
because successfully generating C is not enough when the translator emits a
no-op for an unclassified instruction.

## Repositories compared

The Ascension PC port provided the US digital ELF job-module extractor and
the `0xA00` WWS-policy entry analysis. Its PS3Recomp fork is the job lifter
used for these overlays. The pinned upstream runtime supplied the SPURS job
dispatch and overlay-signature path; M7.90 adapts the hardcoded policy-image
check to the actual registered identities. The C8 PM remains a separate
native lift and is not treated as equivalent to the NPUA PM based on a
different fingerprint.

## What the build can prove

The IPA build can prove that all 31 translated overlays compile, are linked
into the ARM64 Mach-O, and are registered by the app's runtime. It cannot
prove that the iPhone reaches a SPURS job, draws an RSX command, presents a
guest flip, or displays a frame. Those require a device run; a successful
build or launcher screen is not a rendering result.

The IPA does not bundle the game data. In the launcher, select the folder
containing the user's game files so the VFS can mount it; then launch the ELF.
The guest entry point remains `0x003C4FA4`. A runtime `.bin` export is not
required: overlays are converted to native C at build time and linked into
the app. The title should only request a dumped missing-module `.bin` if the
runtime actually encounters an unregistered module.
