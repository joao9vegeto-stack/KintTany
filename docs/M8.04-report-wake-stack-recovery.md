# M8.04 — SPURS report wake and SPU worker stack recovery

Status: source change and regression coverage prepared for the next iOS build. Rendering is **not yet validated**; only an iPhone run with guest draws, a guest flip, and a visible game frame can close that gap.

## What M8.03 actually established

The 23 October M8.03 report is from commit `3cc424998596d9272d660621ac996dbd1447e129` and a 46-second iPhone session:

| Signal | M8.03 result | Meaning |
| --- | ---: | --- |
| Native AOT calls / PPC interpreter | 4,986,634 / 0 | Native guest functions ran; `0x0066640C` is only the latest function entry, not the live instruction PC. |
| `func_00419AC8` wait backedge | 1,106,668 samples | The PPU repeatedly sleeps for 30 µs and returns to `0x00419D1C`. |
| Last sampled wait state | `r6=0` | The ELF loop compares this loaded state to `-1` before leaving; the sample does not identify the producer that should change it. No forced state write is safe. |
| Direct WWS taskset candidates / accepted | 0 / 0 | No direct taskset job was admitted in that interval. |
| POSIX SPU worker stacks | 1 at 256 MiB; 5 at default | Five workers fell back to Darwin's small default stack after `pthread_create` rejected the 256 MiB request. |
| GCM park/SPU holds | 0 | M8.03's self-JUMP park hypothesis was not active in this run. |
| Guest RSX draws / presented flips | 0 / 0 | No game frame was rendered. |

The loop's loaded completion state is reached through the guest pointer at `0x00A23584`, then a word at offset `+4`; the last hook captured `r6=0`. This is a concrete wait state, not evidence that `0x0066640C` is the current PC. The remaining unknown is which guest producer must change that word.

## M8.04 code changes

1. **SPURS wake on RSX report.** The current `gow-ascension-pc` tree includes patch `0026`, which calls `spurs_external_event()` when the RSX writes a guest report. That event clears SPURS idle back-off and wakes the policy coordinator so WWS jobs polling an `RsxBarrier` can observe the report promptly. The AscensionRecomp runtime did not contain this event path. M8.04 ports it and reports RSX report events and SPURS instances woken.
2. **Bounded SPU stack retry.** A failed 256 MiB stack reservation now retries 64, 32, and 16 MiB before the old 512 KiB default. Per-size attempts, successful thread creations, failures, fallback use, and the last pthread/attribute error are reported. This preserves large stacks where available while avoiding an immediate fallback to a stack already known to be too small for deep lifted SPU paths.
3. **No synthetic progress.** The guest wait sentinel is not overwritten; no draw, flip, or rendered frame is fabricated. The existing no-render result remains the acceptance baseline until a device run proves otherwise.

Regression tests exercise both behaviors: a simulated RSX report clears idle state and wakes only initialized SPURS instances; a simulated `pthread_create` rejects 256 and 64 MiB, then succeeds at 32 MiB without using the default stack.

## M8.04 device acceptance

The next report should be read in this order:

- SPU stack metrics: verify the six workers use 256/64/32/16 MiB stacks and whether any still fall back.
- SPURS GPU-report wake: verify the RSX emitted reports and the event woke active SPURS instances.
- Wait-loop sample and taskset counters: determine whether the wait exits and whether direct task work starts.
- Rendering: require guest draws `>0`, presented guest flips `>0`, and an actual game image. A valid IPA, Metal drawable, vblank, filesystem reads, or AOT calls do not satisfy this gate.

All work remains on `AscensionRecomp`. The commercial ELF, assets, and generated game code stay private and are not added to the repository or CI.
