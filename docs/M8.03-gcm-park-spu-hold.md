# M8.03 — FIFO park, SPU task handoff, and wait-loop evidence

**Branch:** `AscensionRecomp` only. **Baseline:** M8.02, commit `7906917eb23f63a714b700c0f778bf361be1a7ce`.

## What the M8.02 report proves

The supplied 48-second report has 5,184,437 PPU AOT calls and reads 11,523,910 bytes through guest `cellFsRead`, but it records zero WWS taskset returns, zero guest draws, and zero guest flips. Six WWS runners started and remain marked active. This is a running native process, not a rendered frame.

`0x0066640C` is the latest AOT function entry in that report. It is an HLE import stub and the report explicitly says the current instruction PC was not measured. The last syscall was `sys_timer_usleep(30)` from `func_00419AC8`; that alone did not prove the PPU remained in that loop.

## Changes

| Area | M8.02 | M8.03 |
|---|---|---|
| RSX segment handoff | Bounded 50 ms hold at `GET_REPORT` existed; the patched self-JUMP park could still start the next FIFO segment while prior SPU task work remained active. | Adds the Ascension PC port’s bounded 50 ms hold at that patched park. The live report counts hold pauses, release after SPU completion, and timeout. |
| PPU wait evidence | `0x0066640C` was the last entry; only a different tree-search loop had a backedge hook. | Adds a hook at `func_00419AC8` backedge `0x00419D1C` and captures the guest GPRs, CR, LR, and CTR at the last sampled backedge. The snapshot is labeled as sampled state, not the current PC. |
| macOS SPU worker stack | The pinned runtime requested 256 MiB, but it silently fell back to the Darwin default if the custom stack or thread creation failed. The report did not show which path each job took. | Reports attempts, accepted 256 MiB attributes, threads created with that stack, fallback attempts, and successful fallback threads. |

## Reference comparison

- The [Ascension PC patch 0017](https://github.com/arnaldolima1/gow-ascension-pc/blob/main/patches/ps3recomp-0017-gcm-park-spu-hold.patch) describes the same race: a zero-cost RSX can reach the next segment before SPU taskset work from the previous frame finishes. M8.03 ports that bounded handoff and exposes its outcome.
- The [GoW II macOS SPU registration](https://github.com/andrebrumdev/gow2-recomp/blob/main/recomp_mid_v2/gow2_spu_register.c) reports deep lifted SPU call chains exceeding Darwin’s 512 KiB default. The [pinned PS3Recomp worker](https://github.com/sp00nznet/ps3recomp/blob/39a36296511c445707adabcd312f0b740cfbd694/runtime/spu/spu_workload.c) already requests a 256 MiB stack, then silently retries the default on failure. M8.03 measures whether this build actually used the requested stack; it does not repeat a size change that is already present.
- The [GoW II SPURS M2 postmortem](https://github.com/andrebrumdev/gow2-recomp/blob/main/notes/SPURS_M2_FINDINGS.md) shows why a loop address alone is not a diagnosis: its first suspected wait was not the active blocker, and the actual wait was identified from a live backtrace and memory inspection. M8.03 samples the known Ascension `usleep(30)` loop and its full guest register context.
- The reviewed [gowa-pc performance patches](https://github.com/RichardFontoura/gowa-pc/tree/main/patches) add gated SPURS/DMA tracing; they do not contain this Ascension FIFO park handoff.

## Verification and limit

The host regression compiles and runs the park logic through pause, task-completion release, 50 ms timeout, and reset. A source test checks that the `func_00419AC8` hook lands exactly once at `0x00419D1C`. The iOS build must also compile the pinned runtime, include all new telemetry symbols in the final ARM64 Mach-O, and pass IPA ZIP integrity checks.

These gates prove the code and package were built. They cannot prove that an iPhone rendered the game. That requires a device report showing guest draws greater than zero, guest flips greater than zero, and the game image. M8.03 is designed to make the next device result identify whether the stall is the PPU wait loop, a FIFO/SPU handoff, or a worker-stack fallback.
