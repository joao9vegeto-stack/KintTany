# M7.98 RSX report and SPU task synchronization

## Evidence from M7.97

The attached run lasts 54 seconds and reports 85,276 admissions to WWS policy
module worker slots across eight workload IDs. The counter increments before
the worker wakes; it does not prove that a module returned or that a game job
ran. The report also has zero calls to the generic SPURS job-chain dispatcher,
zero guest draws, and zero guest flips. The generic job-chain counter does not
count WWS policy admissions, so those are separate paths. The video shows the
black game surface and report UI.

The report does not capture whether the RSX reached `NV4097_GET_REPORT`
(`0x1800`) or which SPU tasks were active at that instant. It therefore cannot
prove that this was the exact wait that held this particular run.

## Functional change

The Ascension PC port's patch 0029 documents a concrete frame-start race:
`RsxSync` uses GET_REPORT to signal post-process tasksets. A fast RSX can reach
the next report while the previous SPU round is still in its barriers. The
next task signals can then be consumed by the previous round, leaving the guest
waiting for the frame label. The iOS runtime did not have that bounded report
hold.

M7.98 ports that behavior into the iOS FIFO worker. A guest GET_REPORT waits
for up to 50 ms while signalled taskset work remains active, then proceeds; the
wait is an explicit FIFO state and is excluded from the stuck-get recovery
path. ZPASS reports (type 1) bypass the hold because they do not signal task
work; the Ascension PC port's later patch 0042 found that holding those reports
starves the RSX. `GCM_REPORT_HOLD_ALL=1` remains an opt-in diagnostic override.
WAIT_SIGNAL now rechecks its guest signal bit every 2 ms, and the runtime counts
active taskset work plus signals pending for parked tasks. When the last task
returns to WAIT_SIGNAL, the RSX worker is woken to retry the same report.

This changes synchronization and preserves the guest's report, signal, task,
and FIFO commands. It does not fabricate a report, task completion, draw, or
flip.

## What still requires the device run

M7.97 proves the PPU entry remains live, the C8 policy is resolved and
dispatched, and files are read. It does not record the report method or
individual WWS job body entries, so it does not establish which of those
stages is the first one missing. The attached video also cannot show internal
guest GPU commands.

The IPA must be run on the iPhone with the same game folder. A successful
first-frame result still requires guest draw and presented guest flip counts
above zero plus video of the game image. An Actions build alone is not that
evidence.
