# AscensionRecomp M6.5 — private writable guest memory, strict PPU40

Hardware screenshot of M6.4.2 2026-10-16: GOWA.ELF NPUA80918,
M6.2 16/16 OK, M6.3 24/24 OK, M6.4 28/32 then safe stop
-995 at guest PC=0x10584, 0x93AB0000 = stw r29,0(r11).
This is not an unknown opcode: M6.4 intentionally supported stw
ONLY in its 4KiB private synthetic guest stack, not writable PT_LOAD.
No evidence yet whether r11 is within PS3 ELF RAM.

M6.5 preserves old 4/8/16/24/32 CPU paths and latest organized UIKit.
New ar_ppu_bootstrap_forty replays privately selected ELF, up to 40
steps, copies only bounded PS3 values into local GPR state. Guest
memory access:
- 4KiB emulated stack at 0x07000000, reads and writes in isolation.
- PT_LOAD ELF segments validated by ar_private_elf_inspect with flags,
  p_filesz/p_memsz bounds, overlapping ranges disallowed.
- New at-most-128-entry sparse aligned word overlay for stw into
  PF_W PT_LOAD ranges, including zero-initialized BSS. It NEVER
  writes to ELF input, host pointers, iOS filesystem, or code pages.
- lwz and ld read overlays first and original segment content second;
  uninitialized BSS read as zero.
- Invalid/misaligned/unmapped/readonly access fails immediately;
  diagnostic includes guest effective address (EA), guest base
  register, source register value, PC and raw opcode. No fake NOP.

Host synthetic PPC64 fixture exactly performs 0x93AB0000 and verifies
PT_LOAD store+readback, BSS write+readback, read-only ELF immutable,
unmapped/readonly/misaligned rejects. Native commercial execution
MUST still be tested on device; if r11 is unmapped, progress correctly
stops with details to guide actual guest allocator/VFS design.
No game code/ELF/RAP in GitHub/IPA. No HLE/SPU or gameplay yet.
