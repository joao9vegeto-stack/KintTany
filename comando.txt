Analisei o `diagnostico-build-67.txt` na raiz da branch `XOWUE`. O `CODE_AUDIT_B67` e o `XOWUE_STALL_THREADS` revelaram a causa EXATA do deadlock entre a Main Thread (`0xF8000001`) e a Thread 2 (`0xF8000008`):

### PROVA EXATA DO QUE ACONTECEU NA BUILD 67 (`diagnostico-build-67.txt`):

1. **Na Build 67, o watchdog acordou a Main Thread (`tid=0xF8000001`, `wait_calls` subiu de `45` para `59 -> 66 -> 72 -> 79`), MAS a Main Thread voltou imediatamente para `bl 0x82C4BE30` (`wait_obj=0xF8000011`) por causa das instruções em `0x829F636C..0x829F63A4` (`CODE_AUDIT_B67`):**
   ```ppc
   0x829F636C: 393F0008  addi  r9, r31, 8       ; r9 = r31 + 8 (flag de conclusão da tarefa assíncrona!)
   0x829F6388: 807F0004  lwz   r3, 4(r31)       ; r3 = FEvent (handle 0xF8000011)
   0x829F638C: 48255AA5  bl    0x82C4BE30       ; FEvent::Wait(INFINITE) -> lr = 0x829F6390
   0x829F6390: 7C004828  lwarx r0, 0, r9        ; lê *(uint32_t*)(r31 + 8) quando acorda!
   0x829F6394: 38000000  li    r0, 0
   0x829F6398: 7C00492D  stwcx. r0, 0, r9
   0x829F639C: 2F0B0000  cmpwi cr6, r11, 0      ; checa se a Worker Thread já concluiu a tarefa em *(r31 + 8)!
   0x829F63A0: 419EFFE8  beq   cr6, 0x829F6388  ; SE *(r31 + 8) == 0, VOLTA PARA 0x829F6388 E DORME EM 0xF8000011 DE NOVO!
   ```
   A Main Thread está em um loop (`0x829F6388..0x829F63A0`) esperando que a **Thread 2 (`tid=0xF8000008`)** execute a tarefa, escreva `!= 0` em `*(uint32_t*)(r31 + 8)` e sinalize `0xF8000011`!

2. **E POR QUE A THREAD 2 (`tid=0xF8000008`) NÃO EXECUTOU A TAREFA?!**
   Olhe para a Thread 2 em `XOWUE_STALL_THREADS` (`RUNTIME seq=1559`):
   ```text
   tid=0xF8000008 state=waiting_event fn=0x82C4BD50 prev=0x82C4BE30 lr=0x829F0698 sp=0x7005FE90 wait_obj=0xF8000007 obj_guest=0x7E006000 obj_creator_lr=0x82C4BCD4 obj_signals=12 wait_calls=1 caller_chain=0x829F0698->0x82C4C42C
   ```
   E olhe para os bytes de `0x829F0684..0x829F06AC` da Thread 2 (`CODE_AUDIT_B66`):
   ```ppc
   0x829F0684: 807F002C  lwz   r3, 0x2C(r31)    ; FEvent (handle 0xF8000007)
   0x829F0690: 3880FFFF  li    r4, -1           ; timeout = INFINITE
   0x829F0694: 4E800421  bctrl                  ; FEvent::Wait() -> lr = 0x829F0698
   0x829F0698: 817F0000  lwz   r11, 0(r31)
   0x829F069C: 7FE3FB78  mr    r3, r31
   0x829F06A0: 816B0008  lwz   r11, 8(r11)
   0x829F06A4: 7D6903A6  mtctr r11
   0x829F06A8: 4E800421  bctrl                  ; EXECUTA A TAREFA QUE A MAIN THREAD ESTÁ ESPERANDO!
   ```
   **Veja o absurdo em `tid=0xF8000008`:**
   - O evento `0xF8000007` teve **`obj_signals=12` (foi sinalizado 12 vezes!)**, mas a Thread 2 (`0xF8000008`) tem **`wait_calls=1`** e NUNCA ACORDOU de `waitGuestObject`!
   - Por quê?
     a) Porque na Build 67 você escreveu `if (isMainThread && currentSwaps == lastSwapCount)` no watchdog de `waitGuestObject`, **deixando a Thread 2 (`tid=0xF8000008`, `wait_obj=0xF8000007`), a Thread 3 (`0xF8000009`, `wait_obj=0xF800000A`) e a Thread 4 (`0xF800000D`, `wait_obj=0xF800000E`) de fora do watchdog!**
     b) E porque em `0x829F6354..0x829F6368` (ou em `0x82C4BD50..0x82C4BE60`), um `ResetEvent` (`KeResetEvent` / `NtClearEvent`) ou `SetEvent` antes da Thread 2 entrar em `waitGuestObject` apagou `waitable->signaled = false` antes da Thread 2 adquirir o lock (lost wakeup)!

### EXECUTAR IMEDIATAMENTE AS CORREÇÕES PARA A BUILD 68:

#### TAREFA 1: ACORDAR A THREAD 2 (`0xF8000008`) E TODAS AS WORKER THREADS EM `waitGuestObject` + IMPEDIR LOST WAKEUPS (`Runtime/XOWUEEngine.cpp`)
1. **Impedir Lost Wakeup em `GuestWaitable`:**
   - Adicione `uint64_t signalGeneration = 0;` em `GuestWaitable`.
   - Toda vez que o evento for sinalizado (`KeSetEvent`, `NtSetEvent`, `signalGuestEventHandle`, `signalGuestEventStructure`), incremente `waitable->signalGeneration++` além de definir `waitable->signaled = true`.
   - Quando `KeResetEvent` / `NtClearEvent` for chamado em um evento que tinha `waitable->signaled == true` mas **ainda não foi consumido por nenhum `waitGuestObject`**, mantenha um contador `uint32_t unconsumedSignals` (incrementado no `SetEvent` se `unconsumedSignals == 0`, decrementado quando `waitGuestObject` acorda uma thread) OU não permita que `ResetEvent` apague um sinal que acabou de ser disparado se houver uma thread prestes a esperar!
2. **Estender o Watchdog de `waitGuestObject` para TODAS as Threads Bloqueadas em Eventos durante Stall Gráfico:**
   - Em `waitGuestObject`, remova a restrição `if (isMainThread && ...)`!
   - Quando `currentSwaps == lastSwapCount` (nenhum swap novo nos últimos 32ms):
     - Se **QUALQUER thread** (`isMainThread` OU worker thread como `0xF8000008` esperando `0xF8000007`, `0xF8000009` esperando `0xF800000A`, `0xF800000D` esperando `0xF800000E`) estiver esperando em `waitGuestObject` por 32ms sem acordar:
       - Sinalize o `waitable` (`waitable->signaled = true; waitable->signalCount.fetch_add(1u);` e grave `1` em `waitable->objectAddress + 4`), bombeie `pumpGuestXenosRingBuffer()`, logue `XOWUE_WAIT_WATCHDOG_WAKE tid=0x%08X wait_obj=0x%08X lr=0x%08X` (primeiras 64 vezes) e retorne `kNtStatusWait0`!
       - **IMPORTANTE:** Acorde as **Worker Threads (`!isMainThread`, especialmente `0xF8000008`) ANTES da Main Thread** (use 16ms de timeout de watchdog para Worker Threads e 32ms para a Main Thread!), para que a Thread 2 (`0xF8000008`) acorde primeiro, execute `0x829F0698 -> 0x829F06A8`, preencha `*(r31 + 8) = 1` e sinalize `0xF8000011` naturalmente para a Main Thread!

#### TAREFA 2: DUMP COMPLETO DE `0x829F6300..0x829F63C0`, `0x82C4BCD0..0x82C4BE80` E `0x829F0600..0x829F0720` + DESTRAVAR `0x829F6388..0x829F63A0`

   - No boot (`CODE_AUDIT_B68`), faça o dump de todas as instruções PowerPC (sem pular nenhuma!) de:

2. **Garantia contra loop infinito em `0x829F6390` (`lr=0x829F6390`):**
   - Quando a Main Thread (`isMainThread`) chamar `waitGuestObject` no evento `0xF8000011` (vindo de `caller_chain` contendo `0x829F6390`), se a Main Thread já tiver esperado nesse mesmo evento `0xF8000011` mais de **8 vezes sem que `g_xenosFrontend.swaps` aumente**:
     - Leia `r31` (ou o ponteiro do objeto `FAsyncTask` na pilha da Main Thread no frame de `0x829F6390`: `sp` de `0x82C4BE30` é `0x7001FC70`, verifique `PPC_LOAD_U32(0x7001FC70)` -> frame de `0x829F6390`, e inspecione os valores salvos na pilha e em `[r31 + 0..0x20]`).

#### TAREFA 3: THROTTLE DE 2ms NO LOOP DE ÁUDIO DA THREAD 4 (`0x82DC314C` / `0x82DC2390`) PARA NÃO SUFOCAR A CPU
No `diagnostico-build-67.txt`, a Thread 4 (`tid=0xF8000014`) inicializou os 34 blocos (`XOWUE_POOL_ALLOC_82DC2BF0`) com sucesso e entrou no seu loop de tick normal (`0x82DC3104..0x82DC3154`), mas como não há `sleep` no tick de áudio, ela executou `0x82DC1FA0` / `0x82DC2390` **471.737 vezes** em poucos segundos, consumindo 100% da CPU!
- Em `Runtime/XOWUEEngine.cpp` (dentro de `xowue_thread_checkpoint(uint32_t address)`):
  - Quando `address == 0x82DC1FA0u` (ou `0x82DC2390u`) e a thread atual for `g_currentGuestThread` (`tid=0xF8000014`), a cada **64 chamadas**, faça `std::this_thread::sleep_for(std::chrono::milliseconds(2));`!
  - Isso reduzirá o uso de CPU da Thread 4 de 470.000 chamadas/seg para ~32.000 chamadas/seg (liberando 95% do core da CPU para a Main Thread e a Thread 2!).
