### PASSO 2: CORRIJA O BUG CRÍTICO NA MAIN THREAD (`g_currentGuestThread == nullptr`) EM `waitGuestObject` (`Runtime/XOWUEEngine.cpp`)
Olhe o bug que você escreveu na linha 1131 de `Runtime/XOWUEEngine.cpp` no commit `020e9a0`:
```cpp
const bool watchdogThread = g_currentGuestThread &&
    (g_currentGuestThread->id == 1u || g_currentGuestThread->lastGuestLr.load(std::memory_order_relaxed) == 0x82585FB4u);
```
**ISSO É SEMPRE `false` PARA A MAIN THREAD (`tid=0xF8000001`)!**
- Na Main Thread (`tid=0xF8000001`), `g_currentGuestThread` é **`nullptr`** (porque `g_currentGuestThread` só é atribuído nas worker threads criadas em `ExCreateThread`; a Main Thread usa `g_mainThreadState` e `currentTraceThreadId() == 1`)!
- Por causa de `g_currentGuestThread && ...`, a Main Thread (`0xF8000001`) esperando `0xF8000011` (`lr=0x82C4BEB8`) **NUNCA ENTROU NO WATCHDOG** e ficou bloqueada em `waitable->cv.wait(lock, ...)` para sempre!

**Correção obrigatória em `waitGuestObject` (e em `KeWaitForMultipleObjects` / `NtWaitForMultipleObjectsEx`):**
1. Identifique a Main Thread corretamente:
   `const bool isMainThread = (g_currentGuestThread == nullptr);`
   `const uint32_t currentTid = isMainThread ? 0xF8000001u : g_currentGuestThread->handle;`
   `const uint32_t currentLr = isMainThread ? g_mainThreadGuestLr.load(std::memory_order_relaxed) : g_currentGuestThread->lastGuestLr.load(std::memory_order_relaxed);`
2. **NUNCA chame `waitable->cv.wait(lock, ...)` sem timeout em NENHUMA thread quando `!timeout.has_value()`!**
   No Xbox 360 / XeniOS, eventos de VBlank, GPU Fence, RHI Worker e XAudio2 acordam as threads periodicamente.
   Quando `!timeout.has_value()`:
   - Faça um loop com `waitable->cv.wait_for(lock, std::chrono::milliseconds(16), [&] { return canAcquireWaitableLocked(*waitable, threadHandle); })`.
   - Se `wait_for` retornar `true`, adquira normalmente e retorne `kNtStatusSuccess`.
   - Se `wait_for` expirar (16ms sem sinal):
     - Na **Main Thread (`isMainThread`)**: se o último draw/swap da GPU tiver ocorrido há mais de 32ms (ou após 2 slices de 16ms esperando `0xF8000011` ou qualquer outro evento sem novo frame), **sinalize efetivamente o `waitable` (`waitable->signaled = true; waitable->signalCount++;` e se `waitable->objectAddress` for válido em RAM guest, chame `signalGuestEventStructure(base, waitable->objectAddress)`), bombeie a GPU (`pumpGuestXenosRingBuffer()`), dispare o VBlank/GPU interrupt callback se registrado, e retorne `kNtStatusSuccess`!**
     - Nas **Worker Threads (`!isMainThread`)**:
       - Analise pelo `CODE_AUDIT_B66` de `0x829F0660..0x829F06D0` (`lr=0x829F0698`, `wait_obj=0xF8000007`) e `0x82585F70..0x82586000` (`lr=0x82585FB4`, `wait_obj=0xF800000A` / `0xF800000E`) o que essas 3 worker threads fazem quando acordam!
       - Se elas verificam uma fila de trabalho (work queue / command queue) ou se `0xF800000A` é o evento de tick/frame que já teve `wait_calls=56`, sinalize quando apropriado (ou a cada 32ms de stall gráfico) para que a RHI/Worker thread processe os comandos pendentes da Main Thread!
       - CUIDADO: Verifique nos bytes de `0x82585F70..0x82586000` e `0x829F0660..0x829F06D0` se acordar uma worker thread com fila vazia apenas faz ela voltar a dormir (seguro) ou se ela exige um item na fila! Se voltar a dormir em `KeWaitForSingleObject`, coloque um intervalo de 32ms para não gerar busy-wait.
