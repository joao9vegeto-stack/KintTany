## Original Switch ARM64 v458752, independently inspected

The actual 47.6 MB `main.patched.bin` contains these code paths (guest offsets, *not* Mach-O file offsets):

- `main+0xc10690`: resource factory setup; `+0xc10748` extracts compression mode from record flags bits 20..25; mode 4 at `+0xc107c4`; calls the chunk pipeline at `+0xc10d80`.
- `main+0xc10d80`: mode-4 chunk streamer. It asks the upstream reader for a **2-byte** chunk length, assembles per-chunk tasks, reads compressed payload + 10 bytes, sets a per-chunk state `0xa`, and calls `main+0x22cf0d0` from `+0xc10ec4`. Direct MOD0 dynamic RELA/JMPREL lookup identifies that PLT target as **`_ZN2nn2os11SignalEventEPNS0_9EventTypeE`** (`nn::os::SignalEvent`). Therefore the resources traverse **event-driven asynchronous chunk work**. Whether the failure is an unready chunk, wrong cursor, or lifecycle/allocator defect remains *unproven*.
- `main+0xc10818`: constructs the reader adapter on the stack with vtable at `main+0x2a64540`, forwarding to a backing stream at adapter `+0x10`. The vtable's `+0x20` points to `main+0xc09728`. Binary bytes at `main+0xc09728` are `000840f9080040f9041140f980001fd6`, which precisely performs `ldr x0,[x0,#0x10]`, then tail-calls its backing stream's virtual `+0x20`. Hence **the 0-byte result is reported by the backing resource stream**, not the adapter itself.
- `main+0xc108ec`: calls the type-specific resource factory with this adapter.
- `main+0x6e7b60`: G1S parser, `+0x6e7bb0` rejects any header read other than exactly 184 B. `+0x1dbdcac`: G1S parser wrapper returns NULL, then `+0xc1098c` records NULL factory return.

## Correct diagnostic boundary, not a guessed fix

The first missing signal is **the backing stream's exact implementation and per-chunk ready/error state at the failed 184-byte read**. Instrument `main+0xc09728`/backing virtual dispatch, and the mode-4 descriptors at `main+0xc10d80`, using original guest object layout and stable exact-BUILD opcode guards. Correlate compressed chunk count, cursor, pending/done/error states and original first-184-byte content *without replacing resources or bypassing the parser*.

**Do not infer that `SignalEvent` was lost** just because event-driven work exists: the pinned NXNative kernel `dm/host/hle_thread.c` implements SVC `0x11` signal and `0x18` wait. Nor assume a 1/2-chunk threshold: existing observations suggest it but do not prove it. Check worker completion and adapter lifetime first.
